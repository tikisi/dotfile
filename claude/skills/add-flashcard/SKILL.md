# add-flashcard

`~/workspace/flashcards` リポジトリに [hashcards](https://github.com/eudoxia0/hashcards) 形式のフラッシュカードを追加するためのスキル。

## 前提

- リポジトリ: `/Users/tikisi/workspace/flashcards`
- カード本体: `Cards/<分野>/<トピック>.md` (例: `Cards/Math/LinearAlgebra.md`)
- 画像: `Cards/<分野>/img/` 配下に置き、カード本文からは相対パス `./img/xxx.jpg` で参照

## 設計チェックリスト (カードを書く前に必ず確認)

詳細・出典は同じディレクトリの `principles.md` 参照。複雑なカードを生成しそうなとき、ユーザーが大量にカードを作りたいとき、向き不向きで迷うときはそちらを開く。

- [ ] **1 カード 1 事実**。複数事実が混ざっていたら分割する。「X の特徴は?」のような対象が広い質問は、属性ごとにカードを分ける
- [ ] **定義より「予測・動機」を問う**。「○○の定義は?」「○○の役割は?」型ばかりだと字面の暗記で終わる。技術系では (a) コード片や具体例を見せて出力・挙動を予測させる、(b) 「なぜそう設計されたか」「何を解決したか」を起点にする、形に書き換えると応用可能な理解になる
- [ ] **質問は短く、答えはさらに短く**。前置き・言い換えを削る
- [ ] **「What ...?」を避ける**。「Definition of X」「Difference between X and Y」「Advantage of X」のようにテンプレ化する
- [ ] **集合 (○○を全部挙げよ)・順序付き列挙を作らない**。個別事実 or Cloze に分解する
- [ ] **コンテキストはカッコで補う** (例: 「スタックキャッシュの利点 (コンピュータアーキテクチャ)」)。`hashcards` にタグ機能はないので質問本文に埋め込む
- [ ] **似た既存カードと干渉しないか**確認し、必要なら特定情報を加える
- [ ] **1 トピックを多角化**。「X の利点」を作るときは「なぜ利点か」「X の欠点」も提案する
- [ ] **双方向の関係**は順方向・逆方向の両方をカード化する
- [ ] **画像があれば積極的に使う**。図解は本文説明より定着する。同じ図で隠す箇所を変えた複数カードも有効

カード化に向かない内容 (実装勘・デバッグ手順など手を動かして覚える類) をユーザーが入れようとしていたら、一言確認する。

## 手順

### 1. 追加先ファイルを決める

ユーザーが明示していない場合は、まず以下を確認する。

- `ls /Users/tikisi/workspace/flashcards/Cards` で既存の分野ディレクトリを把握する
- 既存ファイルに追記するのか、新規ファイル/ディレクトリを作るのかを尋ねる

新規分野を作る場合は `Cards/<分野>/<トピック>.md` を作成する。

### 2. カード種別を選ぶ

| 種別 | 用途 | 構文 |
| --- | --- | --- |
| Q/A | 一問一答・記述 | `Q: ... \n A: ...` |
| Cloze | 穴埋め (1 文に複数の空欄) | `C: ... [隠す部分] ...` |

Cloze は 1 行内の `[...]` ごとに兄弟カードが生成され、デフォルトでは 1 セッション 1 兄弟しか出題されない (sibling burial)。

### 3. カードを追記する

書く前に **設計チェックリスト** (上のセクション) を満たしているか確認する。複数事実が混ざる、回答が長すぎる、対象が広すぎる、などのサインがあれば分割や言い換えを検討する。

既存ファイルに追記する場合は **末尾に空行を 1 行入れてからカードを書く**。複数カードを続けて書く場合、カード間は空行 1 行で区切れば十分 (`---` 区切りも使えるが任意)。

#### Q/A の最小例
```markdown
Q: 質問文
A: 回答文
```

#### 複数行の回答 (リスト)
```markdown
Q: 線形写像の定義は？
A:
- $f(x + y) = f(x) + f(y)$
- $f(cx) = cf(x)$
```

#### Cloze
```markdown
C: 行列 $A$ の [行列式] は、$A$ による [体積拡大率] を表す。
```

### 4. 数式 (LaTeX) の注意点

KaTeX で描画される。インラインは `$...$`、ディスプレイは `$$...$$`。

**よくあるハマりどころ (README.md にも明記されている):**

- ディスプレイ数式 `$$...$$` の中で改行 `\\` を使うときは **`aligned` などの環境で囲む**。生の `\\` は崩れることがある。
  ```markdown
  A:
  $$
  \begin{aligned}
  a &= b + c \\
  &= d
  \end{aligned}
  $$
  ```
- ディスプレイ数式の中で **行頭が `-` や `+` だと Markdown のリストとして解釈される**。行頭にスペースを 1 つ入れて回避する。
  ```markdown
  A:
  $$
   -x + y = 0 \\
   x - y = 0
  $$
  ```
- 行末スペース 2 個 (`  `) で改行を入れている既存カードが多い。同じスタイルに揃えると差分が綺麗。

### 5. 画像を含むカード

画像は `Cards/<分野>/img/` に置き、Markdown の画像記法で参照する。

```markdown
Q:
![](./img/regular_matrix_problem.jpg)
A:
![](./img/regular_matrix_answer.jpg)
```

- 相対パスはデッキファイルからの相対 (`./img/...`)
- コレクションルート (`Cards/`) からの相対にしたい場合は `@/` プレフィックス: `![](@/Math/img/foo.png)`
- 画像ファイルをユーザーが添付・指定した場合は、まず `Cards/<分野>/img/` にコピー or 配置されていることを確認する

### 6. クリアレビュー (ソースを知らないエージェントによるレビュー)

カードを追記したら、**ソース (元のメモ・書籍の要約・会話の文脈) を読んでいないクリーンなレビュアーエージェント**を起動してレビューさせる。ソースを知らない読者 = 将来の学習者と同じ状態なので、カードが単体で成立するか (前提知識の欠落、曖昧な指示語、答えの一意性) を検出できる。

- Agent ツールで **新規エージェント** (general-purpose など) を起動する。**fork は使わない** (会話コンテキストごとソースを引き継いでしまい、クリアレビューにならない)
- レビュアーに渡してよい情報:
  - このスキルの `SKILL.md` の設計チェックリストと `principles.md` (ベストプラクティスとして読ませる)
  - レビュー対象のカードファイルのパスと、新規追加したカードの範囲 (行番号など)
- レビュアーに渡してはいけない情報: ソースのメモ・原文・要約・会話での議論内容
- プロンプトには「principles.md を読んだ上で、指定カードがチェックリストを満たすか、ソースなしで質問が一意に答えられるかをレビューし、指摘のみ返す (編集はしない)」旨を書く
- 返ってきた指摘は主エージェントが妥当性を判断して反映する。既存カードの修正はユーザー確認必須 (「やってはいけないこと」参照)

### 7. 動作確認 (任意)

追記後、ユーザーが希望すれば以下で挙動を確認できる。

```bash
docker compose -f /Users/tikisi/workspace/flashcards/docker-compose.yml up --build
# http://localhost:8080 にアクセス
```

ローカルで構文だけ確認したい場合は `hashcards` バイナリがあれば `hashcards drill <ファイル>` でも可 (通常は Docker 経由)。

### 8. コミット

ユーザーが明示的にコミットを依頼した場合のみコミットする。メッセージは既存履歴のスタイル (日本語、`[Add] トピック名` など) に合わせる。`git log --oneline -10` で直近の慣習を確認してから書く。

**push は明示依頼があるまでしない。** push されると本番サーバーが次回アクセス時に `git pull` で取得するため影響が出る。

## やってはいけないこと

- `Cards/hashcards.db` を編集・コミットしない (SQLite の学習履歴 DB、`.gitignore` 済み)
- 既存カードの **質問文を勝手に書き換えない** (hashcards はカード本文のハッシュで同一性を判定するため、文を変えると学習履歴がリセットされる可能性がある)。修正が必要なら必ずユーザーに確認する
- LaTeX を含むカードで `$$...$$` の中身を勝手に整形・改変しない (描画が崩れやすい)
